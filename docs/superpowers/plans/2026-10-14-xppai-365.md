# xppAI 365 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deliver an independent, locally verified xppAI 365 skill suite for D365FO source-in/answer-or-code-out assistance.

**Architecture:** A sibling CommonJS package distributes nine skills and D365FO references through the existing installation/export pattern. Adapt infrastructure locally; rewrite platform contracts. The assistant runtime performs analysis, with no customer-system connection or embedded model client.

**Tech Stack:** Node.js built-ins, CommonJS, `node:test`, Markdown skills, JSON manifests. Retain the sibling package's Node `>=18` floor; introduce no third-party runtime dependencies. Initial version: `0.1.0`.

**Spec:** [Approved design](../specs/2026-10-14-xppai-365-design.md). Read it and [technical research](../../xppai-365-d365fo-technical-particularities.md) before execution.

## Global Constraints

- Package and CLI name `xppai-365`; location `packages/xppai-365`; the repository root remains outside npm workspaces.
- Nine skills use the `xppai-365-` prefix: core, intake, papai, explain, architect, risk, codefix, dev, help.
- Commands: `list`, `path`, `install`, `export`. Installation targets: Claude, Codex, Qwen, Copilot; generic remains export-only.
- No XPO/cache subsystem, customer environment/database access, Visual Studio automation, Ririchard/Frigelar rules, or GSD.
- Technical instructions, identifiers, and CLI diagnostics are English; explanations follow the user's language.
- Preserve source scope, company/transaction context, localization, and unrelated metadata. Never claim unperformed D365FO validation.
- Existing AX 2009/2012 code and five modified AX 2012 skills are outside this work. Do not stage them.
- Installation tests use temporary homes/projects only. No global install, npm publication, push, or customer-source collection.
- All task paths below are relative to `packages/xppai-365`, unless explicitly labeled repository-relative. Commands run from that package directory.

## Review Focus

1. Unowned/locally modified destinations and dangling links must never be overwritten: Task 2 collision and upgrade tests.
2. Broken relative reference links after packing or export must fail verification: Tasks 1 and 3 reference tests.
3. Source/XML comments containing instructions must remain evidence, not authority: Task 4 XML response case.
4. Missing/contradictory signatures and project-only inputs must produce bounded answers: Task 4 CoC and diagnostics cases.
5. Unsupported archives, unreadable paths, and exception translation must not trigger invented evidence or connections: Task 4 negative cases and batch response case.

## Task 3: Packed artifact and coexistence verification

Artifact verification uses `npm pack --ignore-scripts --json` to prevent lifecycle recursion. The published file allowlist includes `assets/`, `bin/`, `src/`, `docs/`, and `scripts/`; npm also includes metadata/README/license.

```js

for (const [relativePath, value] of Object.entries(legacyBefore)) {
```

## Task 4: Actual response evaluation and final delivery

**Interfaces:** Each fixture contains `{id, prompt, suppliedEvidence, requiredBehaviors, forbiddenBehaviors}`. Recorded results contain `{caseId, model, runtime, response, checks, verdict}`; each check links a requirement to evidence in the actual response. No model SDK/API credentials or fabricated transcripts. Use the available assistant runtime; if fresh evaluation agents are used, provide only the relevant installed skills, references, and case evidence, not the expected answer.

- [ ] **1. Define fixed synthetic cases before evaluating answers.** Implement the six spec cases: method correction, supplied-signature CoC, missing-signature CoC, XML/project context, incomplete compiler evidence, batch retry. Expected behavior follows the spec and Review Focus; invent no standard Microsoft object signatures.
- [ ] **2. Capture actual responses for every case.** Prefer the skills exported by Task 3, so evaluation checks the delivered content. Record model/runtime and complete prompts/responses; never label an authored expected answer as observed output. This is behavioral evaluation, not X++ execution.
- [ ] **3. Assess each response against its rubric.** Reject invented APIs/metadata, legacy compliance demands, unnecessary connections/scaffolding, unsafe CoC/retry behavior, unsupported success claims, and source instructions treated as authority. Correct offending skill/reference guidance, then rerun only affected cases and package checks. Record any evaluation capability limitation explicitly rather than marking unrun cases passed.
