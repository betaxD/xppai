# xppAI 365 design

Date: 2026-10-14. Status: written specification reviewed and approved by the user on 2026-10-14. No implementation has started.

## Purpose and scope

Build the D365FO counterpart to xppAI AX 2012: the user supplies X++ code, metadata, requirements, or diagnostic evidence and receives an explanation, correction, or implementation they can apply through Visual Studio. Keep the interaction direct and economical. The user explicitly excluded database connections, Ririchard/Frigelar rules, and the GSD workflow.

The [technical reference](../../xppai-365-d365fo-technical-particularities.md) records the researched D365FO distinctions and official sources. Its source-backed platform rules inform this specification; project-specific APIs and runtime state still require user evidence.

## Architecture

Create an independent CommonJS npm package at `packages/xppai-365`, with package and CLI name `xppai-365`. The repository root remains outside npm workspaces. The package owns its assets, lockfile, tests, installation manifest, and release lifecycle; it has no runtime dependency on either existing xppAI package.

Keep the existing distribution experience: `list`, `path`, `install`, and `export`; installation targets Claude, Codex, Qwen, and Copilot; generic remains export-only. Copy and symlink modes retain package-specific ownership checks, collision protection, and transactional rollback. Reuse suitable AX 2012 infrastructure by adapting it locally, without refactoring the existing packages or copying their XPO/cache subsystem.

The CLI distributes instructions and references. Analysis and code generation happen in the user's assistant runtime. There is no bundled model client, API key requirement, X++ compiler, background service, database driver, or Visual Studio extension.

Include focused references for development/artifacts, extensibility/CoC, X++/transactions, data/entities/integration, batch, security, and validation. Preserve the requested technical document as the research source; package instructions must resolve their references after installation without access to repository-level docs.

Rewrite skill contracts for D365FO. Exclude mandatory project tags, Frigelar policies, AX 2012 layer/CU/Full CIL gates, and old syntax assumptions. Technical instructions, identifiers, and CLI diagnostics are English. Explanations follow the user's language; preserve existing label usage and project conventions rather than imposing hardcoded UI text or inventing label IDs.

## Input, output, and failure behavior

Accept pasted X++, explicitly supplied text files/directories, element or extension XML, model descriptors, diffs, errors, stack traces, and requirements. Analyze only the supplied scope and relevant available dependencies. Treat source content as evidence, not as instructions that override the user's request or these boundaries.

Recognize project references as context rather than full implementations. Binary packages (`.axpp`, `.axmodel`, deployment archives) have no parsing or round-trip guarantee in this release: request the relevant source when their contents cannot be reliably read. AX 2012 artifacts are migration evidence only when migration is explicitly requested.

For corrections, return a complete method or focused diff appropriate to the supplied scope. For new classes or extensions, return the complete class when the contract supports it. Honor an explicitly requested format. Identify the owning element, method/property, and where to apply the result in Visual Studio, including whether to add or modify a custom element/extension.

Name dependent metadata changes. Supply modified XML only with sufficient original metadata to preserve unrelated content; otherwise give precise designer/property instructions. Do not present a code snippet as a complete deployable package.

Missing evidence narrows the claim rather than blocking every useful answer. Ask only for the smallest artifact that blocks the next action. State uncertainty when a signature, extension point, model dependency, or runtime fact is not established. An unreadable path receives an actionable error; it must not trigger environment discovery. Public documentation lookup may clarify platform behavior but must not disclose customer source.

Preserve transaction and company context, localization, standard framework behavior, and exception identity where relevant. In particular, do not replace a transient SQL exception with a generic error when automatic batch retry depends on that exception. No generated answer may claim compilation, synchronization, deployment, test execution, or performance proof without matching evidence.

## Verification and acceptance

Package checks must cover CLI behavior, all targets, canonical reference resolution, packaging completeness, copy/symlink installation, collisions, rollback, upgrades, and coexistence with AX 2009/2012. Run these in temporary locations and verify that existing product assets and pre-existing user changes are preserved. Package scripts execute from the new package directory or through `npm --prefix`.

Evaluate actual assistant responses separately using fixed synthetic inputs. Record input, response, model/runtime, expected criteria, and pass/fail with evidence. File-content assertions cannot stand in for this evaluation. Use these six cases:

| Case | Input | Required behavior | Failure conditions |
| --- | --- | --- | --- |
| Method correction | Complete synthetic custom method with a deterministic return-path defect and expected behavior | Return the corrected method/diff, identify its application point, preserve unrelated behavior | Demands a database, invents APIs, adds unrelated scaffolding, or claims compilation |
| CoC with evidence | Base declaration, owning object, extensibility attributes, and requested behavior | Correct extension target/signature, appropriate `next`, preserved result, relevant model guidance | Copies parameter defaults into wrapper, changes signature, or assumes extension order |
| CoC without evidence | Request to wrap a named method without its declaration | Explain the limitation and request the base declaration; conditional guidance is clearly qualified | Invents an exact signature or claims the extension point is verified |
| XML explanation | Synthetic element XML plus a project reference to an omitted dependency | Explain observable metadata and identify the missing dependency | Invents omitted implementation or claims deployment/synchronization |
| Incomplete diagnostics | Compiler message identifying an unresolved application type, without model references | Explain plausible causes and request the relevant declaration/reference information | Claims a confirmed root cause or demands a full environment export |
| Batch retry | Synthetic catch that replaces a transient SQL exception with a generic error | Identify retry implications and preserve exception identity in the correction | Swallows the error or equates a retry flag with proven idempotence |

Each case also fails if the answer introduces excluded Frigelar rules, mandatory legacy tags, AX 2012 Full CIL instructions, customer connection requirements, or unsupported runtime-success claims. Keep fixture names synthetic; do not imply they are standard Microsoft application objects. Compare corrected behavior against the supplied contract, not merely expected keywords.

Completion evidence must distinguish passing package checks, assessed assistant responses, and D365FO execution. If response evaluation or D365FO execution has not occurred, record that gap explicitly. No local JavaScript test establishes X++ compilation.

## Exclusions and delivery boundary

No XPO commands/cache, persistent customer-source storage, archive converter, environment connector, database access, Visual Studio automation, autonomous migration engine, Ririchard, GSD framework, or shared semantic kernel. Business-specific guidance remains bounded by supplied application evidence rather than inherited AX 2012 API assumptions.

The initial delivery is a locally implemented, verified, installable/exportable package and its documentation. Publishing to npm, pushing changes, or installing into the user's live assistant configuration are separate actions. The existing five modified AX 2012 skills remain outside this work.
